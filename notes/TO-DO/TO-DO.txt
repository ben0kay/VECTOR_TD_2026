# Project direction

Rebuild the original Vector TD with:

- Familiar gameplay and code flow.
- Native GameMaker systems where practical.
- Data-driven variations without making the architecture difficult to understand.
- Separate objects for meaningful building categories.
- One generic enemy object for most enemy variations.
- Improved local power networks.
- Expandable world generation, resources, enemies and effects.

Ben must be able to read, understand and modify the project.

# Coding preferences

Ben prefers:

- Complete replacement functions and complete object events.
- A short explanation before every supplied function.
- Compact vertical formatting where it remains readable.
- Enums and switch statements.
- Related variables grouped into small structs.
- Direct instructions such as “create this object” and “replace this event.”
- Comments marking sensible future extension points.
- Familiar GameMaker naming and execution flow.
- Larger, complete implementation batches when the final shape is already known.

Avoid:

- Replacing the same event several times across consecutive steps.
- Deep abstraction without an immediate gameplay benefit.
- Huge generic managers that hide how gameplay works.
- Introducing systems without explaining their purpose and test procedure.
- Supplying partial function fragments unless specifically requested.

State naming should remain familiar:

```gml
global.GameState
global.LevelState
global.CameraState
global.BuildState

PlayerState
EnemyState
BuildingState
```

Use custom visual angles instead of rotating instances directly:

```gml
visual.draw_angle
```

Do not rely on `image_angle` as the main gameplay-facing rotation variable.

# Object strategy

## Enemies

Most enemies use:

```text
o_enemy
```

Definitions control:

- Identity.
- Health and movement.
- Movement layer.
- Targeting policy.
- Attacks.
- Navigation response.
- Abilities.
- Spawn and death behaviour.
- Primitive vector appearance or sprite.

A sprite may be used when supplied. Otherwise, the enemy uses its registered primitive drawing function.

Unique bosses may eventually justify:

```text
o_enemy_boss
```

Do not create one object per ordinary enemy.

## Buildings

Use a shared building parent:

```text
o_building_par
```

Use separate child objects for meaningful categories:

```text
o_cpu
o_wall
o_tower
o_miner
o_refinery
o_storage
o_power_generator
o_power_node
o_support_building
```

Variations inside each category remain data-driven:

```text
tower_basic
tower_laser
tower_triple

miner_carbon
miner_copper
miner_silicon
```

This gives each category readable category-specific events without requiring an object for every individual building.

## 5. Upgrades

Use three distinct progression layers.

### Tower ranks

- Kills grant experience/ranks.
- Veteran towers receive small improvements.
- Decide later whether veteran status survives the level.

### Overclocking

- Temporary or manually controlled tower performance increase.
- Increased power consumption.
- Possible heat, damage or failure risk.

### Local level research

- Larger specialized bonuses.
- Requires an upgrade/research building.
- Lasts only for the current level.
- Examples: shield damage, mining speed and battery capacity.

### Persistent progression

- Small account-wide bonuses.
- Purchased in a lobby or menu.
- Examples: approximately `1.03×` tower damage or small production bonuses.
- Must remain weaker than specialized local research.

# Performance rules

The intended game may contain hundreds of enemies and large maps.

Continue to:

- Use native `mp_grid`.
- Stagger expensive enemy checks.
- Avoid recalculating every enemy on the same frame.
- Avoid full navigation-grid reconstruction after one building changes.
- Avoid full-map instance scans every Step when caching or lower-frequency checks are sufficient.
- Use `IFRAMES` for non-critical periodic work.
- Cull drawing and effects outside the camera.
- Profile before introducing pooling or spatial indexing.
- Test building placement while enemies are actively pathing.
- Test 100, 250 and eventually 500 enemies.
- Test 8192×8192 maps before committing to larger sizes.

Do not reintroduce the abandoned flow-field navigation unless there is a very specific, profiled reason.

# Testing expectations

Every implementation batch should include a clear test:

- What object or script to create.
- What room object must be placed in.
- What key or mouse action triggers the test.
- What should appear visually.
- What debug message is expected.
- What failure conditions to report.

When an error occurs, request the latest complete pushed code and return complete corrected functions/events.

# Scope guard

Before introducing a new abstraction, ask:

1. How did the original Vector TD handle this?
2. Can the original approach be cleaned up instead of replaced?
3. Will Ben understand where the behaviour lives?
4. Does the flexibility support gameplay that is actually planned?
5. Can the system be tested immediately?
6. Will implementing the complete near-term version now prevent repeated rewrites?

If uncertain, begin with the simpler original-style implementation and leave a clear future extension point.
