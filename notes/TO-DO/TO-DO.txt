# Project direction

VECTOR TD 2026 is a tower-defense and fortress-defense game with light simulation systems.

Core gameplay priorities:

1. Build and defend a CPU/base.
2. Fight continuous enemy pressure.
3. Survive increasingly difficult handcrafted major waves.
4. Use specialized towers against different threats.
5. Mine and transport resources.
6. Build local power networks.
7. Develop towers through ranks, overclocking and upgrades.
8. Eventually complete level objectives or survive endless pressure.

The current priority is the enemy/tower combat loop.

Mining, cargo logistics and world generation already have working foundations. Their expansion is temporarily secondary.

# Coding preferences

Ben prefers:

- Complete replacement functions and events.
- A short explanation before each supplied function.
- Compact vertical formatting where readable.
- Enums and switch statements.
- Related variables grouped in structs.
- Direct instructions.
- Comments for future extension points.
- Familiar GameMaker execution flow.
- Large coherent batches instead of repeated tiny rewrites.
- One definition function per enemy or tower.
- Custom `visual.draw_angle`, not `image_angle`.

Avoid:

- Deep abstractions without an immediate gameplay benefit.
- Large managers that hide execution flow.
- Definitions scattered across unrelated scripts.
- One object per ordinary enemy or tower variation.
- Replacing the same function repeatedly.
- Partial fragments when a complete function is practical.

Preferred global state format:

```gml
global.GameState
global.LevelState
global.CameraState
global.BuildState
```

Entity state format:

```gml
PlayerState
EnemyState
BuildingState
```

# Damage and shield model

Damage packets carry:

```gml
DamageType.KINETIC
DamageType.EXPLOSIVE
DamageType.LASER
```

Current effectiveness:

| Damage type | Shield | Health |
|---|---:|---:|
| Kinetic | 0.50× | 1.00× |
| Explosive | 0.75× | 1.00× |
| Laser | 2.00× | 0.25× |

Shield damage is processed before health damage.

Unused raw damage correctly overflows into health when a shield breaks partway through a hit.

This makes:

- Basic and minigun towers effective against exposed health.
- Cannons effective against groups.
- Lasers specialized shield breakers.

Future extensions may add:

- Armour.
- Per-weapon shield/health multipliers.
- Resistances.
- Status effects.
- Shield regeneration.
- Mobile shield generators.

# Performance rules

The game may contain hundreds of enemies and large maps.

Continue to:

- Use native `mp_grid`.
- Stagger expensive checks.
- Delay mass repathing.
- Avoid rebuilding entire navigation systems unnecessarily.
- Use `IFRAMES` for non-critical work.
- Cull drawing and effects outside the camera.
- Maintain alive and queued enemy limits.
- Limit spawns per Step.
- Avoid full-map scans every Step where caching is practical.
- Profile before introducing pooling or spatial indexing.
- Test building placement while enemies are pathing.
- Test 100, 250 and eventually 500 enemies.
- Test 8192×8192 worlds before considering larger sizes.

Do not reintroduce flow-field navigation without a specific profiled reason.

# Scope guard

Before adding a major abstraction, ask:

1. How did the original Vector TD handle this?
2. Can that approach be cleaned up instead of replaced?
3. Will Ben understand where the behavior lives?
4. Does the flexibility support gameplay that is genuinely planned?
5. Can it be tested immediately?
6. Will looking slightly ahead prevent repeated rewrites?
7. Can the system remain data-driven without hiding gameplay flow?

When uncertain, prefer the simpler original-style solution with a clear future extension point.
