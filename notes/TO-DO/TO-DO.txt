## New completed work after the original handover

### Player chassis selection and stat pipeline

- `LevelState.CHASSIS_SELECT` now exists between level initialization and
  ordinary `PLAYING` runtime.
- The map loads behind a centered HUD chassis selection panel.
- Player can select Assault, Heavy, Engineer or Support before gameplay starts.
- One generic `o_player` remains the correct architecture; do not make separate
  player objects for Heavy/Assault/etc.
- `scr_player_chassis` owns static chassis definitions, selection, and the
  base/persistent/level/final stat pipeline.
- `player.chassis.stats.final` is rebuilt from base plus flat/multiplier
  persistent and level modifiers; do not modify final stats directly.
- Live runtime currently receives movement speed, HP, shield, weapon damage,
  weapon cooldown, projectile speed and chassis colour.
- Chassis-specific vector silhouettes are now drawn for Assault, Heavy,
  Engineer and Support.
- MMB uses the generic `scr_player_alternate_ability_update()` switch. The
  four secondary abilities currently remain harmless `// FUTURE:` placeholders.
- Main fire remains the player's regular damaging attack. Engineer repair is a
  future secondary ability, not a main fire.

Current baseline stats:

| Chassis | Speed | HP | Shield | Main damage | Cooldown | Secondary |
|---|---:|---:|---:|---:|---:|---|
| Assault | 7.0 | 100 | 0 | 27 | 0.16 | Combat Burst |
| Heavy | 4.8 | 175 | 50 | 20 | 0.22 | Rocket |
| Engineer | 6.4 | 85 | 0 | 15 | 0.20 | Repair |
| Support | 6.0 | 110 | 25 | 18 | 0.18 | Command Pulse |

### Tower turn/aim system

- Towers now turn toward targets rather than snapping instantly.
- `scr_tower_aim_update()` uses shortest-path angle math across `0/360`.
- Towers fire only when their remaining angle difference is within the aim
  tolerance.
- Optional tower definition fields:

```gml
turn_speed_degrees_per_second: 360,
fire_angle_tolerance_degrees: 3,
```

- Missing values default to `360` degrees/second and `3` degrees.
- Basic Tower currently has a deliberate slow test setting of `60` degrees/sec
  and `2` degrees tolerance. The rest currently use defaults until balanced.

### Minimap static terrain and enemy radar contacts

- Dead cells are no longer scanned/drawn individually every minimap frame.
- `hud.minimap.static_terrain` owns a cached surface, dirty flag, scale, width
  and height. It rebuilds on first use, surface loss or zoom changes.
- HUD cleanup frees the cached terrain surface.
- The minimap now has a radar sweep with `sweep_angle`, `previous_sweep_angle`
  and `sweep_degrees_per_second` (currently `90`, so a four-second rotation).
- Enemy contacts only appear when swept, then fade until the next pass.
- Enemy minimap colour always comes from `enemy.visual.color`.
- Enemy definitions may optionally add:

```gml
minimap:
{
    size: 1.5,
    fade_time: 4
},
```

- Missing minimap data defaults to size `1.5` and fade time `4` seconds.
  Runtime stores `size`, `fade_time`, and `contact_remaining`.
- This contact/fade behavior applies only to enemies. Player, buildings and
  terrain remain normally visible.
- In `scr_hud_minimap_update(_hud)`, call
  `scr_hud_minimap_radar_update(_hud)` rather than `id`.

# 2. Project direction

VECTOR TD 2026 is a modern rebuild of the original Vector TD.

It should remain:

- understandable to the user;
- structurally familiar to the original;
- data-driven where it provides clear value;
- easy to expand manually;
- capable of supporting hundreds of enemies;
- centered around fortress and tower defense;
- based on GameMaker MP-grid navigation;
- visually styled around vector primitives;
- compatible with sprites and richer effects later.

Gameplay pillars:

- defend a central CPU;
- move and fight as the player;
- construct walls, foundations, towers and infrastructure;
- extract, store, refine and fabricate resources;
- manage local energy networks;
- supply ammunition to towers;
- survive baseline pressure, clusters and major waves;
- combine tower defense with light simulation and logistics.

Riftbreaker may inspire mechanics, but the project should still feel like the user’s original Vector TD.

Do not turn the game into an abstract framework that the user cannot follow.

# 4. Strict architecture rules

The user explicitly does not want broken architecture hidden by defensive “self-healing” code.

## Required ownership model

`o_controller_main` owns permanent runtime:

- `global.vtd`;
- global tick;
- databases;
- settings;
- persistent game state;
- data initialization.

`o_controller_level` and `scr_level_initialize()` own level runtime:

- `global.vtd_level`;
- map configuration;
- navigation;
- spatial collision;
- entities;
- combat statistics;
- resources;
- build limits;
- energy;
- result tracking;
- current-world runtime.

Instance Create events own their own instance runtime.

## Do not silently repair missing required systems

Consumers must not construct missing owner data.

Examples of forbidden patterns:

```gml
if (!variable_struct_exists(global.vtd_level, "combat"))
{
    global.vtd_level.combat = { ... };
}
```

inside an enemy, projectile, spawner, HUD or result consumer.

Also avoid:

```gml
if (!variable_instance_exists(_enemy, "modifiers"))
    _enemy.modifiers = [];
```

inside a modifier-use function when enemy initialization was supposed to create it.

Required behavior:

- owner creates the runtime once;
- consumers validate it;
- missing required runtime returns `false`;
- log a clear error at the appropriate boundary;
- do not silently cover the mistake.

## Initialization functions

A dedicated initializer may populate its own subsystem, but it must be called by the owner.

Correct:

```text
scr_level_initialize()
    creates spatial configuration
    calls scr_spatial_collision_initialize()
```

Incorrect:

```text
projectile query
    notices spatial system is missing
    initializes it
```

## Optional data is different

Documented optional/default data is allowed when intentional.

Examples:

- optional primitive draw function;
- optional sprite;
- optional status effect;
- optional line-of-sight cache for enemies that use it;
- optional build-menu ordering;
- optional special ability data.

Defaults must be explicit and must not conceal a missing required system.

# 5. Known architecture cleanup still outstanding

The current project works, but several ownership issues should be cleaned later.

## Spatial collision

Improved in the supplied ZIP:

- `global.vtd_level.spatial_collision` is now declared by `scr_level_initialize()`;
- `scr_level_initialize()` calls `scr_spatial_collision_initialize()`;
- initialization failure stops level initialization;
- enemies register when created;
- enemies update registration in End Step;
- enemies unregister during cleanup;
- player and tower projectiles query nearby spatial sectors.

Still outstanding:

## Combat statistics

Currently some systems can create missing `global.vtd_level.combat` data:

- enemy spawner initialization;
- mission-result initialization;
- enemy reward/death handling can add missing fields.

Desired:

```gml
combat:
{
    kills: 0,
    credits_earned: 0
},
```

must be declared completely by `scr_level_initialize()`.

Consumers should only validate and update it.

## Mission results

`scr_level_result_initialize()` is currently invoked by multiple result consumers.

Desired:

- level initialization creates/initializes mission-result runtime once;
- tracking, drawing and result-opening functions only use it;
- consumers do not recover a missing result system.

## Energy ownership

The level runtime declares energy, while the energy controller may also replace the whole energy struct.

Desired:

- `scr_level_initialize()` owns the complete energy runtime;
- `o_controller_energy` validates it;
- controller Create assigns only `energy.controller = id`;
- it does not overwrite the owner’s struct.

## Enemy modifiers

Enemy initialization should always create the modifier array.

Modifier application should fail loudly if the array is missing rather than silently creating it.

## Build-limit defaults

`scr_build_limit_data_defaults_apply()` deliberately adds missing build-limit metadata.

This is currently an intentional convenience, not an accidental recovery system.

Later decide whether every building must explicitly declare:

```gml
build_limit:
{
    type: BuildLimitType.TOWER,
    amount: 1
}
```

Explicit data is more transparent; automatic defaults are more convenient.

# 9. Enemy spatial collision

Recently implemented to optimize projectiles.

Current configuration lives in `global.vtd_level.spatial_collision`:

- adjustable cell size;
- initial enemy radius;
- query padding;
- debug draw flag;
- runtime columns and rows;
- enemy DS grid;
- tracked maximum enemy radius.

Current behavior:

1. Level creates the spatial configuration.
2. Level initializes the grid.
3. Enemy Create registers the enemy.
4. Enemy End Step moves registration when its sector changes.
5. Enemy Cleanup unregisters it.
6. Player and tower projectile segments query only relevant sectors.
7. Exact segment-versus-circle collision chooses the earliest enemy.

Current tuning value:

```gml
cell_size: 256
```

This is intentionally easy to change in level initialization.

Performance result observed after implementation:

- player-projectile all-enemy scanning disappeared;
- projectile cost dropped substantially;
- approximately 50 enemies produced much healthier profiling results.

Outstanding spatial improvements:

- remove lazy initialization calls from consumers;
- add a reusable spatial-radius query;
- reuse that query for attack areas, status-effect splashes, radar and shock foundations;
- consider a structure grid only if hostile projectiles/building counts become expensive;
- add optional debug visualization of occupied sectors;
- profile at 150, 200 and 300 enemies.

Do not prematurely spatialize every system.

Expected hunter behavior:

1. Acquire a strategic building.
2. Check whether the player is in range, visible and reachable.
3. Roll once for player interest.
4. On success, pursue the player.
5. Forget the player when invalid, unreachable or beyond forget range.
6. Return to building strategy.
7. Reconsider a meaningfully closer building constructed along the path.
8. Avoid target thrashing.

Flyers may ignore ground obstruction for visibility and movement according to their rules.

Siege units may ignore the player entirely.

# 27. Special enemies

## Phasers

- ignore buildings;
- still respect permanent terrain unless explicitly configured otherwise.

## Brainless enemies

- travel indefinitely in one direction;
- do not request paths;
- die or attack on impact.

## Splitters

- spawn configured child enemies on death;
- children launch in evenly distributed directions;
- children use brainless movement.

## Transporters

- carry and release smaller enemies.

## Shield-support enemy

- targets buildings at standoff distance;
- shields nearby allies;
- moves to another building when its current strategic target is destroyed.

## Siege Beam Platform

- uses separate hull and turret angles;
- finds a reusable combat anchor;
