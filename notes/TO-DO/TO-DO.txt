This project is a modern rebuild of the original Vector TD. It should preserve the original game’s understandable structure, gameplay feel, enemy pressure, MP-grid navigation, building categories and expanding fortress loop.

The rebuild improves the original with:

- data-driven definitions;
- reusable category objects;
- enums and switch statements;
- related variables grouped into structs;
- local energy networks;
- modernized enemy behaviors;
- reusable vector visuals and HUD components;
- cleaner inheritance;
- modular scripts without excessive abstraction.

If the original project is not available in a new chat, ask the user for:

`VECTOR RTS TD.zip`

Inspect it when implementing or comparing old mechanics. Use its gameplay and behavior as the reference—not necessarily its old code quality.

# 1. Core design rules

## Preserve the original Vector TD identity

The user wants:

- a fortress-defense/tower-defense game;
- large maps and large enemy counts;
- continuous baseline pressure;
- clusters and major waves;
- resource extraction and logistics;
- defensive construction;
- player-controlled movement and combat;
- varied enemy targeting;
- MP-grid navigation;
- gradual expansion from a small base;
- mechanics familiar from the original Vector TD.

Do not redesign this into a highly abstract framework that becomes difficult for the user to understand.

## Preferred code style

Use:

- complete replacement functions and events;
- direct instructions;
- enums and switch statements;
- structs for related runtime values;
- Macros when appropriate to save re-writing code in multiple places
- one definition function per tower or enemy;
- compact vertical formatting when applicable;
- useful `// FUTURE:` comments;
- custom `draw_angle` instead of `image_angle`;
- custom draw_scale instead of image scale (for when sprites are introduced)
- descriptive names such as `GameState`, `LevelState` and `BuildingState`.

Avoid:

- tiny repeated patches to the same function;
- unnecessary manager layers;
- duplicate function names;
- one object per tower or enemy variation;
- flow-field navigation;
- unexplained large code dumps;
- using `power` as a variable name, because `power()` is a GameMaker function.

Use `energy` for the runtime electrical system.

Enums such as `BuildingType.POWER_NODE` and `BuildMenuCategory.POWER` are safe and may remain named that way.

# 2. Main architecture

## Global controller

`o_controller_main` owns permanent application runtime data, including:

- `global.vtd`;
- the global tick;
- databases;
- major game state;
- persistent systems;
- data initialization.

## Level controller

`o_controller_level` owns one active level through:

`global.vtd_level`

This includes:

- elapsed time;
- world configuration;
- navigation;
- resources;
- combat and kills;
- wave pressure;
- energy networks;
- build state;
- level-specific modifiers.

## Generic gameplay objects

Current structure intentionally uses category objects:

- `o_building_par`
- `o_tower`
- `o_wall`
- `o_miner`
- `o_storage`
- `o_foundation`
- `o_energy_generator`
- `o_energy_node`
- `o_energy_battery`
- `o_enemy`
- `o_projectile_tower`
- `o_projectile_player`
- `o_pickup`

Different towers and enemies should normally be definitions using these objects, not separate objects for every variation.

## Inheritance pattern

A child building Step Event should normally resemble:

```gml
event_inherited();

if (!instance_exists(id))
    exit;

if (!BUILDING_CAN_OPERATE)
    exit;

scr_tower_update(id);
```

Use the appropriate category update function for miners, storage and other building types.

Navigation intentionally resembles the original game.

Implemented:

- breach grid;
- flying navigation;
- dead terrain obstacles;
- building obstacles;

- brainless movement;
- obstruction attacks.

Do not reintroduce the abandoned flow-field architecture unless the user explicitly requests it.

## Intended targeting examples

The system should support:

- enemies that prefer the CPU;
- enemies that prefer nearby buildings;
- enemies that sometimes choose the player;
- phasers that ignore buildings but not terrain;
- flyers that ignore ground obstacles;
- underground enemies with their own restrictions;
- breachers that attack a blocking structure when the CPU is sealed;
- siege units that stop at long range.

## Size and corridor handling

Most ordinary enemies currently use simple collision radii.

For future oversized enemies, prefer behavior design over extremely complicated clearance grids:

- siege units attack from range;
- large kamikazes hit the first structure;
- flyers ignore ground corridors;
- underground units use their own traversal;
- bosses may use dedicated movement logic.

Only add multi-cell clearance navigation if a future enemy genuinely requires it.

# 15. Upgrade vision

The upgrade system should eventually have several layers.

## Tower veterancy

Already founded through:

- individual tower kills;
- ranks;
- small stat improvements.

Veterancy should reward long-lived towers without becoming the main source of power.

## Overclocking

Future local control that may:

- increase fire rate;
- increase damage;
- increase range;
- greatly increase energy consumption;
- generate heat;
- risk temporary shutdown.

## Level-local research

Stronger upgrades that last for the current level.

Examples:

- laser towers deal more shield damage;
- miners extract faster;
- batteries discharge faster;
- walls gain armour;
- anti-air rockets gain splash;
- towers consume less idle energy.

These may require an upgrade or research building.

## Persistent progression

Smaller permanent bonuses earned outside a level.

Examples:

- all towers deal `1.03x` damage;
- buildings gain a small HP bonus;
- starting credits increase slightly;
- research unlocks new towers or enemies in testing modes.

Persistent upgrades should be weaker than level-local research.
