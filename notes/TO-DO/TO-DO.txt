# Coding preferences

Ben prefers:

- Complete replacement functions and object events.
- A short explanation before supplied code.
- Compact vertical formatting where readable.
- Enums and switch statements.
- Related variables grouped in structs.
- Direct instructions.
- Comments for sensible future extensions.
- Familiar GameMaker execution flow.
- Complete batches rather than repeated incremental rewrites.
- Custom `visual.draw_angle` instead of gameplay relying on `image_angle`.

Avoid:

- Deep abstractions without an immediate benefit.
- Large managers that hide gameplay flow.
- Definitions scattered across unrelated scripts.
- One object per ordinary enemy or tower variation.
- Replacing the same function several times in consecutive steps.
- Partial code fragments when a complete function can reasonably be supplied.

Preferred state names:

```gml
global.GameState
global.LevelState
global.CameraState
global.BuildState

PlayerState
EnemyState
BuildingState
```

# Data organization

## Enemy data

Most enemies use:

```text
o_enemy
```

Enemy definitions live in:

```text
scr_enemy_data
```

Each enemy now receives its own definition function:

```gml
scr_enemy_data_weak()
scr_enemy_data_hunter()
scr_enemy_data_phaser()
scr_enemy_data_shooter_single()
scr_enemy_data_shooter_triple()
scr_enemy_data_kamikaze()
scr_enemy_data_splitter()
scr_enemy_data_splitter_child()
scr_enemy_data_flyer()
```

The initializer should remain a simple readable registration list:

```gml
function scr_enemy_data_initialize()
{
    global.vtd.data.enemies = {};

    scr_enemy_data_weak();
    scr_enemy_data_hunter();
    scr_enemy_data_phaser();
    scr_enemy_data_shooter_single();
    scr_enemy_data_shooter_triple();
    scr_enemy_data_kamikaze();
    scr_enemy_data_splitter();
    scr_enemy_data_splitter_child();
    scr_enemy_data_flyer();

    return true;
}
```

Future enemies should require only:

1. One new enemy definition function.
2. One new initializer call.

Enemy primitive drawing functions belong in:

```text
scr_enemy_visual
```

Sprites remain optional. Primitive visuals remain the fallback.

## Building data

Non-tower building definitions live in:

```text
scr_building_data
```

This currently includes:

- Walls.
- Miners.
- Storage buildings.
- Future utility, research and power buildings.

All definitions still register into:

```gml
global.vtd.data.buildings
```

## Tower data

Every tower definition lives in:

```text
scr_tower_data
```

Each tower receives a separate function:

```gml
scr_tower_data_basic_ground()
scr_tower_data_anti_air()
```

The initializer is a readable registration list:

```gml
function scr_tower_data_initialize()
{
    scr_tower_data_basic_ground();
    scr_tower_data_anti_air();

    return true;
}
```

Future towers should require only:

1. One new tower definition function.
2. One new initializer call.

Tower runtime behaviour belongs in:

```text
scr_tower
```

Primitive tower drawing functions belong in:

```text
scr_tower_visual
```

Do not recreate or use:

```text
scr_combat_expansion_data
```

That temporary script mixed enemy and tower definitions based on implementation timing rather than gameplay category. Its contents have been moved into the proper data scripts.

Initialization order:

```gml
scr_enemy_data_initialize();
scr_building_data_initialize();
scr_tower_data_initialize();
scr_resource_data_initialize();
scr_world_data_initialize();
```

`scr_building_data_initialize()` creates the shared building database first. `scr_tower_data_initialize()` then adds tower definitions using `variable_struct_set()`.

## Upgrades

Keep three progression layers:

### Tower ranks

Kills and experience create small veteran bonuses.

### Overclocking

Temporary performance increase with additional power demand and possible heat or risk.

### Local research

Larger specialized level-only bonuses from research buildings.

Examples:

- Increased shield damage.
- Faster mining.
- Increased battery capacity.

### Persistent progression

Small account-wide bonuses researched or purchased outside levels.

Persistent bonuses should remain weaker than specialized local research.

# Performance rules

The intended game may contain hundreds of enemies and large maps.

Continue to:

- Use native `mp_grid`.
- Stagger expensive checks.
- Avoid simultaneous mass repathing.
- Avoid full navigation-grid reconstruction after one building changes.
- Avoid full-map instance scans every Step where caching is practical.
- Use `IFRAMES` for non-critical work.
- Cull drawing and effects outside the camera.
- Profile before introducing pooling or spatial indexing.
- Test placement while enemies are actively pathing.
- Test 100, 250 and eventually 500 enemies.
- Test 8192×8192 worlds before considering larger maps.

Do not reintroduce the abandoned flow-field navigation without a specific profiled reason.

# Scope guard

Before adding a major abstraction, ask:

1. How did the original Vector TD handle this?
2. Can that approach be cleaned up instead of replaced?
3. Will Ben understand where the behaviour lives?
4. Does the flexibility support gameplay that is actually planned?
5. Can it be tested immediately?
6. Will completing the near-term version prevent repeated rewrites?

When uncertain, use the simpler original-style approach and leave a clear extension point.
