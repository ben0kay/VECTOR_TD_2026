# 1. Project direction

VECTOR TD 2026 is a modern rebuild of the user’s original Vector TD.

It should remain:

- understandable to the user;
- structurally familiar;
- data-driven where useful;
- easy to expand;
- suitable for hundreds of enemies;
- focused on fortress defense;
- based on MP-grid navigation;
- visually styled around vector primitives;
- open to sprites and particle effects later.

The game combines:

- tower defense;
- fortress construction;
- player movement and shooting;
- resource extraction;
- logistics;
- local energy networks;
- enemy pressure and major waves;
- light simulation mechanics;
- future research and progression.

Do not redesign it into an overly abstract framework.

# 2. Preferred coding style

Use:

- complete replacement functions and events;
- direct instructions;
- enums and switch statements;
- related variables grouped into structs;
- macros where they remove genuine repetition;
- one registration function per tower;
- one registration function per enemy;
- compact vertical formatting;
- small, useful comments;
- `// FUTURE:` hooks;
- custom `draw_angle`;
- custom `draw_scale` when sprites are introduced.

Prefer names such as:

- `GameState`
- `LevelState`
- `PlayerState`
- `BuildingState`
- `EnemyState`

Avoid:

- repeated tiny patches to the same function;
- duplicate function names;
- one object per tower variation;
- one object per enemy variation;
- unnecessary manager layers;
- flow-field navigation;
- unexplained large code dumps;
- variables named `power`, because `power()` is built into GameMaker.

Use `energy` for electrical runtime data.

Enums such as `BuildingType.POWER_NODE` remain safe.

# 11. Immediate next step — reusable combat anchors

The next implementation should be a reusable combat-position system.

Its first user will be the Siege Beam Platform.

## Desired beam-tank behavior

The enemy should behave like a tank with two independently drawn pieces:

- hull;
- turret.

The hull faces movement.

The turret continues facing the target.

When approaching a target:

1. Select the target building.
2. Search for a useful firing position.
3. Confirm a valid route to that position.
4. Confirm the target remains within firing range.
5. Determine whether a usable sideways strafe lane exists.
6. Travel to the combat anchor.
7. Fire continuously.
8. Move left and right along the lane.
9. Reverse at endpoints or unexpected obstructions.
10. Keep the turret aimed at the target.
11. Re-evaluate when the target or terrain changes.

If no suitable strafe location exists, the enemy must still function.

## Use a strafe lane, not a clear circle

Do not require an entirely clear 128-pixel-radius circle.

Use a line-shaped movement lane:

```text
LEFT LIMIT <------ ANCHOR ------> RIGHT LIMIT
                         |
                         | beam
                         v
                       TARGET
```

The lane is perpendicular to the direction between the anchor and target.

The requested lane length should be configurable.

Example:

```gml
combat_movement:
{
    type: EnemyCombatMovement.STRAFE,

    preferred_range: 520,
    minimum_range: 420,
    maximum_range: 620,

    preferred_lane_length: 128,
    minimum_lane_length: 64,

    speed_multiplier: 0.7,
    arrival_tolerance: 8,

    reverse_pause_minimum: 0.1,
    reverse_pause_maximum: 0.35,

    search_cooldown_seconds: 1.5
}
```

Interpret `preferred_lane_length: 128` as total length, approximately 64 pixels on either side of the anchor.

## New combat-movement enum

Recommended:

```gml
enum EnemyCombatMovement
{
    STATIONARY,
    STRAFE,
    ORBIT,
    KITE
}
```

This is separate from:

- `EnemyMovementLayer`;
- `EnemyAbility`;
- `EnemyAttack`.

`EnemyMovementLayer` describes where an enemy travels.

`EnemyCombatMovement` describes what it does while fighting.

`EnemyAbility` contains optional capabilities.

## Runtime structure

Recommended direction:

```gml
enemy.combat_movement =
{
    type: EnemyCombatMovement.STRAFE,

    anchor:
    {
        x: 0,
        y: 0,
        valid: false,
        target: noone,
        navigation_revision: -1
    },

    lane:
    {
        left_x: 0,
        left_y: 0,
        right_x: 0,
        right_y: 0,

        length: 0,
        direction: choose(-1, 1)
    },

    search:
    {
        cooldown_remaining: 0,
        failed_attempts: 0
    }
};
```

Visual runtime should support:

```gml
enemy.visual.hull_angle
enemy.visual.turret_angle
```

Keep `visual.draw_angle` as a compatibility value, normally matching `hull_angle`.

## Candidate search

Do not scan every pixel.

Sample a limited number of candidate positions around the target at useful firing distances.

For every candidate:

1. Convert it to a world/grid position.
2. Reject blocked terrain.
3. Reject occupied positions.
4. Confirm firing range.
5. Confirm MP-grid reachability.
6. Calculate the perpendicular strafe lane.
7. Sample the lane at cell-sized intervals.
8. Shorten the lane if only part is usable.
9. Reject it if shorter than the minimum length.
10. Optionally test line of sight at the center and endpoints.
11. Score the surviving candidate.

Candidate scoring may prefer:

- distance close to preferred range;
- longer lane;
- clear line of sight;
- shorter travel distance;
- less nearby siege-unit crowding;
- fewer sharp route changes.

Start with a small candidate count. Expand only if testing shows it is necessary.

## Fallback hierarchy

The system must degrade safely:

1. Full preferred strafe lane.
2. Shortened valid strafe lane.
3. Stationary combat anchor.
4. Existing stop-at-range behavior.
5. Breach behavior if firing range cannot be reached.

Strafing is a bonus behavior, not a requirement for attacking.

## Performance rules

Combat anchors must not search every frame.

Search only when:

- a new target is acquired;
- the current anchor is invalid;
- the target is destroyed;
- the navigation revision changes;
- the enemy becomes stuck;
- a search cooldown expires after failure.

Use staggered retries so multiple advanced enemies do not search on the same frame.

Once anchored:

- do not create a new MP path for every strafe step;
- use direct short movement along the validated lane;
- reverse at endpoints;
- reverse when unexpectedly blocked;
- retain normal collision checks.

## Soft anchor reservations

Future improvement:

Combat anchors may be softly reserved.

This should discourage multiple siege units from choosing exactly the same anchor without making the position a permanent solid obstacle.

Other enemies must still be able to pass through.

Possible data:

```gml
global.vtd_level.navigation.combat_anchors
```

Only add shared reservations after the single-enemy version works.

## Line of sight

If dead terrain blocks the beam, validate line of sight from:

- anchor center;
- left endpoint;
- right endpoint.

If endpoint line of sight fails, shorten that side of the lane.

Do not continuously perform expensive full-line checks unless profiling shows they are affordable.

# 13. Enemy behavior architecture improvement

As advanced enemies grow, separate their concerns:

```text
Strategic target
    ↓
Navigation objective
    ↓
Combat anchor
    ↓
Combat movement
    ↓
Attack behavior
    ↓
Abilities and effects
```

Examples:

- strategic target: closest building;
- navigation objective: combat anchor;
- combat movement: strafe;
- attack: continuous beam;
- ability: regeneration.

This prevents one enum or ability from controlling the enemy’s entire identity.

Avoid immediately rewriting every enemy.

Introduce the combat-anchor foundation for the beam tank first. Generalize it only after it works.

# Additional continuity notes

## Communication and work method

When supplying code:

- briefly explain what each function or event does before its code block;
- prefer complete replacement functions/events;
- clearly state where every function belongs;
- state which objects, scripts or events the user must create;
- avoid instructions such as “add this somewhere inside the function”;
- look slightly ahead and implement related changes together;
- avoid repeatedly replacing the same function over several tiny steps;
- keep code compact vertically where readability permits;
- inspect the newest GitHub push before every substantial implementation.

The user normally pastes the supplied code into GameMaker and pushes it to GitHub for verification.

## State naming

The user prefers:

```gml
global.GameState = GameState.PLAYING;
global.LevelState = LevelState.PLAYING;
```

Do not replace these with visually awkward nested fields such as:

```gml
global.vtd.LevelState
```

Use custom runtime fields such as:

- `visual.draw_angle`;
- future `visual.draw_scale`;
- future `visual.hull_angle`;
- future `visual.turret_angle`.

Avoid `image_angle` and unnecessary use of GameMaker’s built-in image scaling.

## Room-layer placement

The intended gameplay-room layer order includes:

- `Controller`
- `Effects_Flyer`
- `Projectiles_Flyer`
- `Enemies_Flyer`
- `Instances`
- `Effects_Ground`
- `Projectiles_Ground`
- `Player`
- `Enemies_Ground`
- `Buildings`
- `Foundations`
- `World`
- `Background`

Placement rules:

- buildings belong on `Buildings`;
- foundations belong on `Foundations`;
- dead cells and resource nodes belong on `World`;
- ground enemies/projectiles/effects use their corresponding ground layers;
- flying enemies/projectiles/effects use their corresponding flying layers;
- the player belongs on `Player`.

Do not return to spawning everything on `Instances`.

## Movement layers and abilities

`EnemyMovementLayer` represents physical traversal:

- `GROUND`
- `FLYING`
- `UNDERGROUND`

Phasing is an ability or effect, not a movement layer.

This distinction lets towers determine whether they can attack an enemy while abilities independently modify navigation.

Flying enemies should:

- visibly hover;
- ignore ground buildings and dead terrain for navigation;
- be targetable by anti-air defenses;
- be attackable by anti-air towers over intervening dead terrain.

## Navigation decisions

Keep native MP-grid navigation.

The earlier flow-field experiment caused severe building-placement stalls and was intentionally abandoned.

Use:

- normal ground grid;
- breach grid;
- flying navigation;
- staggered repathing;
- navigation revisions;
- cached paths where possible.

Large-enemy movement was discussed. The current decision is not to build complex multi-cell-clearance navigation prematurely.

Prefer enemy designs that naturally avoid corridor problems:

- large siege enemies operate at range;
- large kamikazes strike the first obstruction;
- flyers ignore ground corridors;
- underground enemies use another traversal layer;
- bosses may receive bespoke movement.

Only implement multi-cell path clearance when a real enemy requires it.

## Target selection

Enemy targeting must remain configurable.

Supported or planned behaviors include:

- direct CPU targeting;
- closest-building targeting;
- weighted selection among nearby buildings;
- occasional player targeting;
- phasers preferring the CPU;
- siege enemies selecting buildings;
- underground enemies preferring miners;
- support enemies positioning near allied enemies;
- breach targeting when a strategic target is blocked.

Some enemies may choose among the nearest several buildings rather than always selecting the absolute closest one.

Target acquisition should not perform unnecessary full-map scans every frame. Cache targets and retarget only when needed.

## Hull and turret separation

Advanced enemies may have two independent orientations:

```gml
visual.hull_angle
visual.turret_angle
```

The hull faces movement.

The turret faces the combat target.

`visual.draw_angle` may remain as a compatibility alias for the hull angle.

This is immediately relevant to the Siege Beam Platform and may later be reused by:

- advanced shooters;
- rocket platforms;
- tanks;
- gunships;
- bosses;
- mobile support units.

## Enemy ability composition

Enemies may contain several abilities because `abilities` is an array.

However, some current special behaviors return early from `scr_enemy_update()`. Combining certain behaviors may therefore require composition work.

Long-term enemy update direction:

1. target selection;
2. navigation objective;
3. combat anchor;
4. combat movement;
5. attack behavior;
6. passive ability updates;
7. effects;
8. death abilities.

Do not assume that adding two values to the ability array automatically makes every combination function correctly.

## Shields

Shielding is not a unique enemy type.

Any compatible enemy can receive a shield through:

- its definition;
- a spawn modifier;
- a support shield generator;
- future level modifiers.

Natural shields and temporary support shields remain separate runtime pools.

Enemy health-bar drawing should show both when applicable.

## Towers and line of sight

Ground towers may be blocked by dead terrain when line of sight is required.

Anti-air towers should be able to engage flying targets over dead terrain because the target is airborne.

The player may shoot over friendly `o_wall` structures, but player projectiles should be blocked by:

- dead terrain;
- resource terrain;
- CPU;
- ordinary buildings.

Future projectile behaviors may independently configure:

- piercing;
- wall traversal;
- terrain traversal;
- splash;
- line attacks;
- target-position attacks.

## Attack-area system

The intended reusable attack shapes are:

- point;
- circle;
- line;
- cone;
- capsule.

These should eventually support:

- direct hits;
- explosions;
- shockwaves;
- continuous beams;
- piercing lasers;
- flamethrowers;
- area denial;
- boss attacks.

Gameplay collision and damage must remain independent from particles.

## Level data

Each level should eventually have one relatively easy-to-edit definition containing:

- starting resources;
- maximum resources;
- world-generation settings;
- available buildings;
- available towers;
- available resources;
- available enemies;
- baseline pressure;
- clusters;
- sequential waves;
- milestones;
- modifier unlock times;
- grace period;
- scaling;
- victory conditions.

The development level may temporarily expose all content.

Real levels should introduce towers, enemies and resources gradually.

## Wave intentions

Major waves should be sequential and progressively harder.

Wave definitions may be handcrafted, for example:

- 50 weak enemies;
- 20 shooters;
- 4 siege enemies.

Weighted pools remain useful for baseline pressure and some flexible wave groups.

Major waves should arrive automatically. Manual triggering belongs to the debug interface.

## Fortress and progression vision

The game is influenced by the underlying gameplay ideas of The Riftbreaker, without attempting its graphical complexity.

Desired long-term layers include:

- base construction;
- local energy distribution;
- isolated outposts;
- batteries;
- mining;
- logistics;
- tower defense;
- enemy pressure;
- research;
- persistent progression.

Upgrade types discussed:

- tower veterancy from kills;
- tower ranks with small bonuses;
- tower overclocking;
- strong level-local research;
- weaker persistent upgrades between levels.

Example:

- persistent: all towers deal `1.03x` damage;
- local research: laser towers deal 15% more shield damage.

## Important historical fixes

Past problems worth avoiding:

- accessing struct fields before verifying they exist;
- using GameMaker built-in function names as variables;
- duplicating function definitions;
- drawing runtime-only tower data inside HUD preview structs;
- reading destroyed targets after validating them earlier in the frame;
- releasing world grids after the grid was already destroyed during game shutdown;
- placing Draw GUI code inside the HUD Step Event;
- forgetting to create/register a new script asset before calling its functions.

Use defensive field checks where optional data is expected.
