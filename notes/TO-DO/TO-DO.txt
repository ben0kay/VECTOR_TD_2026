# VECTOR TD 2026 — REBUILD ROADMAP

## Project direction

Rebuild the original Vector TD with familiar gameplay, recognizable code organization, and selective improvements.

The original `VECTOR RTS TD.zip` is the primary gameplay and structural reference. Preserve systems that already worked well before replacing them.

### Core rules

- Keep the project understandable and familiar.
- Implement one playable system at a time.
- Prefer complete functions and events.
- Use enums and readable switch statements for states.
- Group related variables into small structs.
- Keep major state variables direct and familiar:

```gml
global.GameState
global.LevelState
global.CameraState

PlayerState
EnemyState
```

- Use data-driven variations where they remove duplicated objects.
- Keep separate objects for meaningful building categories.
- Use native `mp_grid` navigation like the original game.
- Profile before introducing complicated optimization systems.
- Avoid abstract systems without an immediate gameplay purpose.

# Architecture

## Persistent game runtime

Owned by `o_controller_main`:

```gml
global.vtd.tick
global.vtd.settings
global.vtd.data
global.vtd.debug
```

Future persistent data:

```gml
global.vtd.profile
global.vtd.upgrades
global.vtd.statistics
```

## Current-level runtime

Owned by `o_controller_level`:

```gml
global.vtd_level.time
global.vtd_level.map
global.vtd_level.navigation
global.vtd_level.entities
global.vtd_level.resources
global.vtd_level.waves
global.vtd_level.power
```

This data is recreated for every gameplay level.

## Data-driven objects

### Enemies

Most enemies share:

```text
o_enemy
```

Enemy definitions determine:

- Identity
- Stats
- Movement layer
- Target preference
- Attack type
- Navigation response
- Vector appearance or sprite
- Abilities
- Spawn/death behaviour

Unique bosses may later use:

```text
o_enemy_boss
```

### Buildings

Use separate objects for meaningful building categories:

```text
o_building_parent
o_cpu
o_tower
o_wall
o_miner
o_refinery
o_storage
o_power_generator
o_power_node
o_support_building
```

Variations within a category remain data-driven:

```text
tower_laser
tower_triple
tower_electric

miner_carbon
miner_copper
miner_silicon
```

# Scope guard

Before introducing a new abstraction, ask:

1. Did the original Vector TD already solve this effectively?
2. Can the existing familiar solution be cleaned up instead?
3. Does this abstraction make the project easier for Ben to understand?
4. Is the added flexibility required by current gameplay?
5. Can the system be tested immediately?

If the answer is unclear, use the simpler original-style implementation first.
