# 1. Project direction

VECTOR TD 2026 is a modern rebuild of the user’s original Vector TD.

It should remain:

- understandable to the user;
- structurally familiar to the original;
- data-driven where it genuinely helps;
- easy to expand;
- capable of handling hundreds of enemies;
- centered around fortress and tower defense;
- based on GameMaker MP-grid navigation;
- visually styled around vector primitives;
- open to sprites and richer particle effects later.

Gameplay inspiration includes the original Vector TD and selected ideas from Riftbreaker:

- defend a central CPU;
- build walls, towers and infrastructure;
- extract and refine resources;
- manage local energy networks;
- survive continuous pressure and major waves;
- move and fight as the player;
- combine tower defense with light simulation.

Do not redesign the project into an overly abstract engine the user cannot follow.

# 2. How to work with the user

The user strongly prefers:

- complete replacement functions and events;

- small useful comments;
- `// FUTURE:` hooks;
- modular scripts separated by responsibility;
- one enemy registration function per enemy;
- one tower registration function per tower;
- inspecting the latest push before coding.

Important:

- The user manually copies code from chat into GameMaker.
- Do not generate replacement project ZIPs or overwrite project files unless explicitly requested.
- Do not repeatedly rewrite the same large function for tiny additions.
- Look slightly ahead and implement a complete phase where practical.
- Avoid scattering endless enemy-specific `if` checks through generic events.
- Use fast flags or optional data only when necessary.
- Do not introduce a new enum or architecture merely because an enemy is visually unusual.
- Preserve the familiar original Vector style whenever a simpler implementation works.

Preferred state naming:

- `global.GameState`

- `PlayerState`
- `BuildingState`
- `EnemyState`

Use custom:

- `draw_angle`
- future `draw_scale`

Do not rely on `image_angle` for gameplay-facing rotation.

Do not use `power` as a runtime variable name because `power()` is a GameMaker function. Electrical runtime uses `energy`.

# 18. Breaching, phasing and special movement

Ground enemies use ordinary MP-grid navigation first.

If a target becomes unreachable:

- delayed blocked-route checking occurs;
- breach targets may be selected;
- enemies attack blocking structures;
- paths recover after the obstacle is destroyed.

Phasing is an ability/effect-like capability, not a movement layer.

Phasing enemies:

- ignore buildings;
- still respect permanent dead terrain unless explicitly designed otherwise.

Brainless enemies:

- move indefinitely in one direction;
- do not target;
- collide with terrain or entities;
- attack on impact;
- may destroy themselves on impact.

# 20. Centipede implementation

The Centipede intentionally remains close to the original Vector implementation.

No new `EnemyBehavior` was added.

## Head

`enemy_centipede_head`:

- is a normal standard building-hunting enemy;
- uses ordinary MP-grid navigation;
- records a fixed-size breadcrumb trail;
- spawns 5–8 children;
- is marked with `is_centipede_head`.

## Children

`enemy_centipede_child`:

- uses the generic `o_enemy`;
- is marked with `is_centipede_child`;
- follows an older head position;
- uses a configurable frame delay;
- performs no targeting or pathfinding while attached;
- is independently targetable and damageable;
- becomes brainless when the head dies;
- continues along its last direction;
- attacks or dies on impact according to normal brainless logic.

Performance:

- ordinary enemies perform only cheap boolean checks;
- ordinary enemies do not enter Centipede update functions;
- only the head records breadcrumbs;
- children do not request MP-grid paths.

Current Step pattern:

```gml
if (
    is_centipede_child
    && scr_enemy_centipede_child_update(id)
)
{
    // Attached child handled.
    exit;
}
```

After ordinary enemy gameplay:

```gml
if (is_centipede_head)
    scr_enemy_centipede_head_update(id);
```

Current Centipede work needs testing.

Verify:

- 5–8 children spawn;
- chain stretches correctly;
- children follow corners;
- children remain targetable;
- destroying a middle child leaves the rest functional;
- head death detaches survivors;
- detached children use brainless collision;
- no child requests an MP path;
- several Centipedes do not cause unusual spikes;
- shields and status effects remain safe;
- wave completion handles surviving children correctly.

Do not add the Centipede to natural pressure until these tests pass.

Already foundational:

- towers track their own kills;
- kills increase rank;
- veteran bonuses should remain small;
- long-lived towers become slightly stronger.

## Overclocking

Future local control:

- stronger output;
- increased energy demand;
- possible heat, wear or downtime;
- reversible during a level.

## Local research

Level-only upgrades from research buildings.

Examples:

- laser towers deal more shield damage;
- miners extract faster;
- batteries discharge faster;
- towers rotate faster;
- walls gain armour;
- drones carry more.

These reset between levels.

## Persistent upgrades

Small permanent bonuses researched in a lobby, campaign or meta screen.

Examples:

- all towers deal `1.03x` damage;
- small construction discount;
- slightly larger storage;
- minor player stat improvements.

Persistent bonuses should remain smaller than local research bonuses.

Do not mix all upgrade types into one system.

# 32. Architecture guardrails

Before adding a new system, ask:

1. Can existing data represent it?
2. Is it a new behavior or merely a visual?
3. Is it an ability that can combine with others?
4. Is it an effect applied temporarily?
5. Does it need a new object category?
6. Will every enemy pay a per-frame cost?
7. Can a fast flag avoid irrelevant function calls?
8. Can the system be reused?
9. Does the original Vector already contain a simpler model?
10. Will the user understand where to edit it later?

Prefer the smallest system that preserves future expansion.

Do not optimize theoretical problems at the cost of readability.

Do not ignore measured performance problems.
