This replaces the old cumulative handover. It records the current architecture, implemented systems, work that still needs testing, and a condensed future roadmap. Inspect the newest GitHub push before changing code because current chat work may be newer than the reviewed commit.

1. Project direction

VECTOR TD 2026 is a data-driven rebuild of the original Vector TD: defend a central CPU while controlling the player, constructing a fortress, managing local energy and logistics, and surviving escalating enemy pressure.

Keep the project:

understandable and manually editable;

based on GameMaker MP-grid navigation;

capable of roughly 100–300 active enemies;

visually compatible with both primitive vector drawing and sprite overrides;

modular without turning straightforward gameplay into an abstract framework.

The original Vector project remains a gameplay and pacing reference, not an architectural template.

2. Working rules

Inspect the newest source before writing code.

Give exact script/event locations and complete replacement functions when ambiguity exists.

Keep GML compact; do not stretch every argument or property vertically.

Preserve unrelated fields when replacing data definitions.

Use one registration function per tower and enemy.

Use structs, enums IF NECESSARY, switches and draw_angle; do not use image_angle as gameplay-facing direction.

Simple booleans to gate logic would be good. Looking for performance over anything else

With dynamic struct string keys, use variable_struct_get/set.

Do not make consumers silently recreate missing required runtime.

Fix compile/runtime errors before expanding systems.

Profile real bottlenecks before introducing caches or spatial systems.

The user normally pastes code into GameMaker manually; do not push or replace project files unless explicitly requested.

3. Runtime ownership

Permanent runtime

o_controller_main owns:

global.vtd;

databases and definitions;

settings and tick state;

profiles and persistent progression.

Level runtime

o_controller_level and scr_level_initialize() own:

global.vtd_level;

world/map data;

navigation grids and revisions;

entities and combat statistics;

resources, storage and build limits;

energy networks;

mission results and level-only upgrades.

Instance runtime

Each instance initializer owns that instance's required state. Consumers may default documented optional data, but must not conceal missing required initialization.

combat/feedback: player, tower and enemy projectiles, effects and world feedback.

Variations normally come from data. All normal enemies use o_enemy; all towers use o_tower; utilities and foundations also use their shared category objects.

Solid inheritance is now:

o_solid_par
├─ o_building_par and building descendants
├─ o_cpu
└─ o_world_solid
   └─ o_dead_cell

The enemy Collision Event targets o_solid_par, so it receives collisions from buildings, the CPU and world-solid descendants. Primitive drawing does not create collisions; assigned sprite masks do.

7. World, collision and navigation

Implemented:

data-driven world definitions;

empty, dead and resource cells;

clustered terrain and weighted/guaranteed resource veins;

CPU safe area and content allowlists;

MP grids for ground, breach and flying movement;

navigation revisions, staggered repathing and breach fallback;

pathing toward CPU, buildings, player and assigned orders;

phasing, brainless movement, standoff/orbit/combat-position movement;

world-solid circle and moving-circle checks.

WorldCellType is logical map data. o_world_solid is instance collision inheritance. They serve different consumers and should not be treated as interchangeable.

Enemy/building collision masks scale from their sprite-mask dimensions to the intended runtime footprint. Primitive visuals are independent of those masks.

17. Performance architecture

Implemented optimizations:

enemy spatial grid for player/tower projectile queries;

exact swept segment collision;

staggered enemy decisions/repaths;

fast camera culling helpers;

cached minimap terrain surface;

event-driven energy topology rebuilds;

static resource-node behavior.

Performance rules:

do not optimize based only on function call count;

profile Draw and Step separately;

compare gameplay with buildings/enemies hidden only to isolate categories;

do not spatialize infrequent placement checks without evidence;

prefer sprite overrides for expensive primitive tower visuals when art becomes available.

Next profile target: a real late-game scene with 100, 200 and ideally 300 enemies, rapid-fire towers, enemy shooters, explosions, logistics and the full HUD visible.

19. Condensed technical cleanup

Only pursue these where the newest code still exhibits the issue:

Make level initialization the sole owner of required combat/result/energy runtime.

Remove consumer-side recovery of missing required systems.

Confirm enemy modifier runtime is always created by enemy initialization.

Remove genuinely unused collision/world helpers only after rg confirms zero callers.

Keep validators from reading optional fields before checking their existence.

Confirm cleanup ordering before destroying grids, paths, lists and surfaces.

Replace enemy-projectile all-building scans only if profiling warrants it.

Add a reusable spatial-radius enemy query if frequent explosions/shockwaves become expensive.

Consider cached/static primitive geometry or sprite overrides only for measured Draw bottlenecks.

20. Polished future roadmap

A. Finish and prove current loops

Complete refinery/fabricator/ammunition playtesting.

Balance energy generation, buffers and network ranges.

Balance tower turn rates, range, damage, cooldown and ammunition use.

Run full pressure/wave playthroughs and fix restart/cleanup defects.

B. Player identity

Assault Combat Burst: temporary fire-rate/damage surge.

Heavy Rocket: aimed explosive secondary with a meaningful cooldown.

Engineer Repair: channel or pulse repair for nearby structures.

Support Command Pulse: temporary shield/energy/targeting support.

Add chassis-specific local and persistent upgrades after abilities are proven.

C. Tower depth

Per-tower upgrade UI built on the existing stat pipeline.

Manual overclock mode: stronger output for greater energy/heat pressure.

Anti-armour tower for heavy targets.

Chain-lightning tower using reusable target chaining.

Hybrid ground/air tower with lower specialization efficiency.

Support tower that buffs nearby towers rather than duplicating Repairer behavior.

More ammunition families only when they create distinct logistics decisions.

D. Enemy variety

Underground miner hunter with detection/counterplay before underground swarms.

Armour-focused elite that makes anti-armour damage meaningful.

Energy disruptor that temporarily stresses local networks or buffers.

Saboteur targeting logistics/storage rather than the nearest combat building.

Simple variants using existing abilities: shielded brute, fast splitter, kamikaze flyer and mixed-cargo transporter.

Minibosses assembled from existing movement, shield, siege and death-ability systems.

Bosses only after ordinary-wave balance and performance are stable.

E. Base and economy expansion

Wind turbine with placement-dependent output.

Larger generator/node/battery/storage tiers.

Research Station for level-only upgrades.

Repair controls and clearer manual maintenance feedback.

Advanced refined materials/components after the basic production chain is fun.

F. Campaign and progression

Campaign map and level selection.

World/biome definitions with distinct terrain and resource pressure.

Content unlocks and research presentation.

Persistent profile upgrades kept smaller than level upgrades.

Save migration/version testing whenever persistent schemas change.

G. Presentation

Preserve primitive fallbacks for missing art and previews.

Add sound, music, better hit audio and construction/alert cues.
